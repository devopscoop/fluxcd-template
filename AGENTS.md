# AGENTS.md

Instructions for AI coding agents working in this repo. `CLAUDE.md` is a symlink to this file — edit this one, and keep the symlink intact (pre-commit's `check-symlinks`/`destroyed-symlinks` hooks will fail if it gets replaced with a regular file).

This is a FluxCD GitOps template: one git repo per cluster. There is no build and no test suite — the "build" is Flux reconciling this repo into a cluster, so correctness work is validating manifests and conventions before commit.

## How a deploy is wired together

Two layers, and both must be edited to ship an app:

1. `flux/flux-system/<app>.yaml` — a Flux `Kustomization` (`kustomize.toolkit.fluxcd.io/v1`) whose `spec.path` points at `apps/<app>`. Every one carries the same SOPS `decryption` block so it can decrypt secrets in that directory.
2. `apps/<app>/` — the actual manifests, assembled by a kustomize `Kustomization`.

`flux/flux-system/kustomization.yaml`'s `resources` list is the on/off switch: an app in `apps/` with a Kustomization in `flux/flux-system/` still does not deploy until its filename is in that list. `deploy.sh` (per-platform app lists) and `deploy_new_app.sh --deploy` both append to it with `yq ... | unique`.

Ordering between apps is expressed with `spec.dependsOn` in `flux/flux-system/*.yaml`, referencing another Kustomization by `metadata.name`. The `*-custom-resources` apps exist precisely for this: CRs that need their operator's CRDs installed first (`cert-manager-custom-resources` → `cert-manager`, `eg-custom-resources` → `eg`, `metallb-custom-resources` → `metallb`, `rook-ceph-cluster` → `rook-ceph`) live in a separate app so they can depend on it. The VictoriaMetrics CRDs go the other way: `victoria-metrics-crds` installs only the CRDs, depends on nothing, and every app that ships VM objects depends on it (see the Monitoring section).

## The Helm app pattern

`apps/templates/helm/` is the boilerplate that `deploy_new_app.sh` copies; `apps/templates/kustomize/` is for plain-manifest apps and is copied by hand. A Helm app directory holds `namespace.yaml`, exactly one of `helmrepo.yaml`/`ocirepo.yaml` (the script deletes the unused one and uncomments the right line in `kustomization.yaml`), `release.yaml`, `values.yaml`, `helm_secrets.yaml`, `kustomization.yaml`, and `kustomizeconfig.yaml`.

The indirection is the part worth understanding. Helm values are *not* inlined in `HelmRelease.spec.values`. Instead `kustomization.yaml` runs `values.yaml` through `configMapGenerator` and `helm_secrets.yaml` through `secretGenerator`, both mapped to the key `values.yaml=`, and `release.yaml` pulls them in via `spec.valuesFrom`. Because the generators append a content hash to the resource names, `kustomizeconfig.yaml` supplies a `nameReference` config that teaches kustomize to rewrite `spec/valuesFrom/name` on `HelmRelease` objects — without it the HelmRelease points at names that don't exist. Keep all four names in sync when renaming an app: the generator names (`<app>-values`, `<app>-secrets`), `valuesFrom`, and the `namespace:` field.

This split is deliberate — it keeps secrets encryptable and lets you prototype the same files with plain Helm:

```shell
helm install <app> <repo>/<chart> --namespace <app> --version <ver> --values values.yaml --values <(sops -d helm_secrets.yaml)
```

Convention for `values.yaml`: strip everything you are not overriding, so the file contains no chart defaults. `apps/templates/helm/values.yaml` ships `dyff`/`vim` one-liners for diffing your file against the chart's defaults.

## Secrets

`.sops.yaml` picks the encryption rule by *filename*, so names are load-bearing:

- `*secrets.yaml` — a real Kubernetes Secret; only `data`/`stringData` are encrypted, so `apiVersion`/`kind` stay readable to the API server.
- `*helm_secrets.yaml` — Helm values that happen to be sensitive; the whole file is encrypted.

Never open an encrypted file in an editor — use `sops <file>`, which decrypts, opens, and re-encrypts. Plaintext staging files use the `.decrypted` suffix, are gitignored, and are swept up by `encrypt_secrets.sh` (via `sops --filename-override`, so the ciphertext lands under the real filename and gets the right rule). Files under `apps/templates/` are skipped. `deploy.sh` calls `encrypt_secrets.sh` during bootstrap and commits the result (including the deletions of the tracked `.decrypted` boilerplate); on an already-bootstrapped repo it only warns about stray `.decrypted` files and leaves encrypting them to `encrypt_secrets.sh`.

## Conditional marker blocks

Optional config ships commented out between `>>> <marker>` / `<<< <marker>` comment delimiters (with a leading hash on the real markers). `toggle_blocks.sh --enable <marker>` strips the leading hash-and-space (or a lone hash) from the lines between them; `--disable <marker>` puts it back. The markers stay in place, so both directions are idempotent. It only transforms files and prints what it touched — no git operations — so `deploy.sh` stages what it prints (the same split as `encrypt_secrets.sh`: the tool owns the mechanism, `deploy.sh` owns the git bookkeeping). Genuine comments inside a block must use a doubled hash (`## like this`); toggling leaves those untouched in both directions. Files under `apps/templates/` are skipped (same as `encrypt_secrets.sh`) — the boilerplate always ships with its blocks commented out. The enabling steps run on every `deploy.sh` invocation, not just bootstrap: an app added later ships with its blocks still commented, and the next run opens (and commits) them. `deploy.sh` never disables — turning a feature back off is a manual run. A block can also be toggled without a full deploy by running `./toggle_blocks.sh --enable <marker>` (or `--disable`) directly; markers can be comma-separated or repeated, and modes mixed (`./toggle_blocks.sh --enable eks --disable slack`). Current markers: `eks` (enabled when `k8s_platform=eks` — EKS-platform config: IRSA service-account annotations, AWS NLB annotations, gp3 storage classes, disabling control-plane scrapes, plus the aws-load-balancer-controller/metrics-server dashboard downloads in `apps/victoria-metrics`), `karpenter` (also enabled when `k8s_platform=eks` — pins spot-intolerant workloads to on-demand nodes via `karpenter.sh/capacity-type`, and gates Karpenter's own dashboard downloads in `apps/victoria-metrics`; a separate marker because those labels exist only on Karpenter-provisioned nodes, and the pinning — or the dashboards, if Karpenter is removed — can be toggled independently of the EKS config), `opencost` (also enabled when `k8s_platform=eks` — OpenCost's dashboard download in `apps/victoria-metrics`, gated with the app like metallb's), `slack` (enabled when `slack_alerts=true` — Alertmanager → Slack in `apps/victoria-metrics`; see its README), `dex` (never auto-enabled — toggled manually once the optional `apps/dex` issuer is deployed; in `apps/victoria-metrics` it turns on Grafana SSO via `auth.generic_oauth` plus a gateway-level OIDC `SecurityPolicy` for the Alertmanager/vmui routes; see `apps/dex/README.md`), `pg-oauth` (never auto-enabled — PostgreSQL 18 native OAuth for developer logins in the CNPG database template, validated against the dex issuer; separate from `dex` because it needs a hand-built validator extension image and Kubernetes 1.35+ image volumes first — enabling it with the placeholder image reference breaks the database pods; see the block's comments and `apps/dex/README.md`), `metallb` (enabled when `k8s_platform` is not eks — MetalLB's dashboard download in `apps/victoria-metrics`, gated with the app), and the per-app dashboard markers `longhorn`, `rook-ceph`, `coraza`, and `uptime-kuma` (never enabled by `deploy.sh` — run `./toggle_blocks.sh --enable <app>` by hand when you enable that opt-in app, so its dashboard turns on with it; its scrapes and rules need no marker, see the Monitoring section), plus `rabbitmq-instances` (inside `apps/rabbitmq-cluster-operator/vm.yaml` — the broker-fleet scrape, enabled by hand when the first RabbitmqCluster ships; see that file's header), `valkey-instances` (the same pattern inside `apps/valkey-operator/vm.yaml`, enabled by hand when the first ValkeyCluster ships), and `spegel` (never auto-enabled — the containerd settings the opt-in `apps/spegel` needs, as nodeadm `userData` in `apps/karpenter-custom-resources/ec2nodeclass.yaml`; enable it in the same commit as the app, and expect every Karpenter node to be replaced, since a `userData` change drifts them; see `apps/spegel/README.md`).

Gotcha, called out in `toggle_blocks.sh` itself: never write the literal opening marker (hash, space, three `>`) anywhere except a real marker. The script greps every tracked file for it and rewrites every file that matches — including prose. When writing about markers in docs, drop the leading hash, as above.

## Monitoring conventions

The default observability stack (`apps/victoria-metrics`) discovers everything through custom resources, and the repo has one pattern for wiring an app into it — three pillars per app:

- **Scrapes** are `VMPodScrape`/`VMServiceScrape` objects, never chart-native ServiceMonitors/PodMonitors: the `monitoring.coreos.com` CRDs are deliberately not installed on a pure VictoriaMetrics cluster (see apps/victoria-metrics/README.md → "CRD ownership"), so enabling a chart's toggle fails the apply. Mirror what the chart's ServiceMonitor would have selected, select on the workload's own `matchLabels` (never `helm.sh/chart`), and mind the port *name*.
- **Alert rules** are `VMRule` objects, adapted from the best upstream source with every deviation documented in the file header (the VMRule in `apps/eg/vm.yaml` is the style reference). Severity is a page label, not a filter — every warning and critical pages GoAlert and Slack — so upstream rule sets get pruned and re-tuned, not copied.
- **Dashboards** — prefer a chart-native toggle (`apps/cnpg`, which the sidecar picks up as a `grafana_dashboard: "1"` ConfigMap — it reads every namespace); otherwise add an entry under `grafana.dashboards` in `apps/victoria-metrics/values.yaml`, which Grafana's download-dashboards init container fetches at every pod start (`gnetId` for grafana.com dashboards, a pinned raw GitHub URL otherwise), with a comment naming what feeds it and any known gaps. Write a ConfigMap dashboard only when there is no upstream to pull (the hand-built envoy/coraza dashboards in `apps/victoria-metrics`, `apps/tempo/dashboard.yaml`).

Placement: VictoriaMetrics is a required part of this template, so every app carries its own scrape/rule CRs — `apps/<app>/vm.yaml`, one file holding all of that app's VM objects, listed in the app's `kustomization.yaml` (a few stack apps predate the name and split them per kind: `vmrule.yaml`, `vmservicescrape.yaml`, ...). The app's flux Kustomization then needs the VictoriaMetrics CRDs first: add `dependsOn: victoria-metrics-crds` — the CRDs only, never `victoria-metrics` itself just for ordering, because the stack needs eg's Gateway API CRDs (a cycle for eg and anything it depends on) and has `wait: true` (a broken Grafana upgrade would hold every dependent app). Depend on `victoria-metrics` only when the app needs the running stack (goalert, tempo, otel-collector, opencost). The Flux control plane has no app directory, so its objects sit in `apps/victoria-metrics/flux-vm.yaml`. When an object targets a namespace other than its app's, say so with `namespaceSelector` — `selectAllByDefault` makes vmagent and vmalert pick objects up from every namespace, but a scrape without a selector only looks in its own. Downloaded dashboards all live in `apps/victoria-metrics/values.yaml` whichever group the app belongs to — the Grafana that downloads them lives there; hand-built ConfigMap dashboards sit wherever fits.

Gating: monitoring for an app that isn't deployed must not apply — an empty scrape pool pages `ScrapePoolHasNoTargets`. Scrapes and rules get that for free by living in the app: they apply exactly when it does. A scrape must still match something whenever its app is deployed — put it in the app that creates its targets (the rook-ceph scrapes live in `rook-ceph-cluster`, not the operator), and keep fleet-wide scrapes of instances no app ships yet in a marker block (`rabbitmq-instances`, `valkey-instances`). Dashboard downloads live centrally under `grafana.dashboards` in `apps/victoria-metrics/values.yaml`, so for platform-conditional and opt-in apps those sit in marker blocks enabled with the app (`eks`/`karpenter`/`opencost` and `metallb` automatically by deploy.sh; `longhorn`/`rook-ceph`/`coraza`/`uptime-kuma` by hand). When adding an app, add its three pillars the same way — and if it's opt-in with a downloaded dashboard, a marker named after it.

## Placeholders that deploy.sh rewrites

On every run, `deploy.sh` calls `replace_placeholders.sh`, which rewrites, most specific form first, `project1-dev.devops.coop` → `$cluster_domain`, `devopscoop-project1-dev` → `$org_name-$cluster_name` (S3 bucket names), `project1-dev` → `$cluster_name`, `us-east-2` → `$region`, and `arn:aws:iam::ACCOUNT_ID:` → `arn:aws:iam::$aws_account_id:` (IRSA role ARNs; skipped while `aws_account_id` is empty) across every tracked file except itself, `deploy.sh`, and this file (they mention the placeholders in prose), then commits and pushes what it changed. It runs on already-bootstrapped repos too, so apps pulled in from the template later get rewritten on the next run. It skips SOPS-encrypted files (editing them in place breaks the MAC) and warns about them instead. Like `toggle_blocks.sh`, it prints the files it changed and does no git operations, so it can also be run by hand with the variables set in the environment. Treat all of these strings as reserved: don't introduce unrelated uses, and don't "fix" them to something else in template files. `deploy.sh` also commits and pushes on its own several times, with `git commit -n` to bypass local hooks; the other one-time bootstrap rewrites are skipped on an already-bootstrapped repo — see the `deploy.sh` bullet under "Other scripts".

## Validation

`pre-commit` is the whole check suite (yamllint, markdownlint, detect-secrets, detect-private-key, symlink checks, plus a local hook).

```shell
pre-commit install                         # once
pre-commit run --all-files                 # everything
pre-commit run validate-flux --all-files   # just the Flux conventions hook
```

`.githooks/validate-flux.py` enforces two rules:

- Every `Namespace` resource needs the `kustomize.toolkit.fluxcd.io/prune: disabled` annotation, so Flux won't delete namespaces (and PVCs with them). Rationale and the counter-argument are in `arguments/prune.argdown`.
- Every `dependsOn` entry must name a Flux Kustomization that exists in `flux/flux-system/`, with no dependency cycles. This check scans that whole directory regardless of which files are staged, so it catches a dangling reference even when you only touched `apps/`.

CI runs one job on pull requests: `.github/workflows/flux-diff.yaml` runs `./flux_diff.sh` (see "Other scripts") and posts the rendered diff as one sticky PR comment through `.github/scripts/flux-diff-comment.js` (README.md → "Continuous integration"). The script's exit code drives the job: 1 (this tree fails to render) fails it; 0 and 2 (only the merge-base fails) pass. Two things about the script are non-obvious and spelled out in its header: flate loads every YAML file in the directory it is pointed at and ignores kustomize `resources` lists, so the script renders through a generated root Kustomization whose `spec.path` is `flux/flux-system`; and because this template ships `resources: []`, the script falls into "template mode" here — every Kustomization whose `spec.path` exists, the tracked `*.decrypted` boilerplate copied to the real filenames, chart schema validation off. So a PR that breaks a kustomization or fails a chart's values schema goes red in CI before Flux sees it, and `./flux_diff.sh` shows the same thing locally.

## Other scripts

- `./flux_diff.sh [-o STYLE] [BASE_REV]` renders the working tree (uncommitted changes included) and the merge-base with `BASE_REV` (default `origin/main`) offline with flate and prints what Flux would apply differently. It renders from copies, so the working tree is untouched. Exit 1 means this tree fails to render, 2 means only the base does. Needs `flate` (Brewfile cask; no Arch package, see pkglist.txt).
- `./deploy_new_app.sh` with no arguments prints its usage; it scaffolds a Helm app from the template, pulls the chart's default values into `values.yaml`, and optionally registers it for deploy (`--deploy`) and adds ImageRepository/ImagePolicy entries (`--image-automation`).
- `./update_flux-instance.sh [FILE]` bumps `flux/flux-system/flux-instance.yaml` to the latest Flux release and re-pins each controller image to its multi-arch digest. Set `GITHUB_TOKEN` to avoid anonymous API rate limits.
- `./deploy.sh` bootstraps a fresh template clone; it requires `variables.sh`, refuses to start on a dirty working tree, and pushes to the remote as it goes. On an already-bootstrapped repo (detected by the `fluxcd-template/bootstrapped` annotation in `flux/flux-system/flux-instance.yaml` *and* its sync URL pointing at `$git_owner/$git_repo` — both stamped by the final bootstrap commit) it skips the one-time rewrites. Every `flux-operator` command — `flux-operator install` plus the `flux-system` githubapp and `sops-age` secrets — runs only with `--update-flux`, so a plain run touches only the repo and needs no cluster access; pass the flag when bootstrapping, after changing `flux-instance.yaml`, or after rotating the GitHub App or SOPS age key. It still runs the placeholder rewrite (via `replace_placeholders.sh`) and the marker-block uncommenting (via `toggle_blocks.sh --enable`), so apps added after bootstrap get their placeholders rewritten and their `eks`/`slack` blocks opened on the next run.
- `./psql-oauth.sh APP -- -c 'SQL'` runs SQL on a CNPG database with the `pg-oauth` block enabled, as the developer's own OAuth role (`runbooks/connect-cnpg-database.md` options 1 and 2), and works without a terminal: it port-forwards, starts psql's device flow, opens dex's approval page in the developer's browser, and returns psql's output once they approve — so allow a few minutes for the run. It connects to a replica through the `-ro` Service by default, where writes fail as read-only; pass `-e rw` for statements that write (the primary), or `-e r` (any instance) on a single-instance Cluster, which has no replicas. Every fresh connection is a new approval, so for more than one or two queries start a session first: `./psql-oauth.sh --session start APP` (one approval, blocks until the developer approves), after which the same `APP -- -c 'SQL'` runs (also `-f FILE`, SQL on stdin, and the output flags `-A -t -x --csv`) are answered through the background psql with no browser, exit 1 on a server error, and `./psql-oauth.sh --session stop APP` ends it when the work is done. A session only answers runs with the same `-n`/`-c`/`-d`/`-U`/`-e` and the same kubeconfig (sessions are per Kubernetes cluster, since dev and prod share names), so when the user says a session is running, first run `./psql-oauth.sh --session status` and reuse the matching line's `ns`/`cluster`/`db`/`role`/`endpoint` as flags — its `issuer` names the environment. `-At` gives machine-readable output. The role defaults to the git email's local part; pass `-U ROLE` when that isn't the developer's role in the Cluster's `managed.roles`.

## Image automation and promotion

In the continuously-deployed (dev) repo, image-automation-controller commits tag updates to `# {"$imagepolicy": ...}` setter markers in `apps/*/values.yaml`. Prod-like repos sync from dev via PR and must not run the automation controllers — leave the marker comments and the `imagepolicies.yaml`/`imagerepositories.yaml`/`imageupdateautomation.yaml` files in place so syncs stay conflict-free, and just don't reference them. Full procedure in README.md → "Promoting changes to other environments".

## Package manifests

This repo ships a `Brewfile` (macOS: `brew bundle`) and a `pkglist.txt` (Arch Linux) that install every CLI tool the repo uses. Keep them in sync with the code:

- When you add a tool, script, or a new external command inside an existing script, add the package to BOTH files, with a comment noting what uses it.
- When a tool stops being used, remove it from both files.
- Verify package names before adding them: `brew info <formula>` for Homebrew, and the official repos/AUR for Arch. Names differ between ecosystems — this repo already depends on two such cases: the Go (mikefarah) `yq` is Arch's `go-yq` (Arch's `yq` is the incompatible Python implementation), and the Flux Operator CLI comes from the `controlplaneio-fluxcd/tap` Homebrew tap and the AUR `flux-operator` package. If a package is AUR-only, note that in pkglist.txt's header instructions.
- Update the "Install required packages" section in README.md if the tool list changes.

Note that the scripts need the Flux Operator CLI (`flux-operator`), not the standard `flux` CLI — the plain `flux` command appears only in commented-out lines.
